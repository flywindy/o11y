## 3. 工作規則

**分支與 PR**
- 每個 PR 一個分支，命名 `claude/<topic>`，從最新的 `origin/main` 開。
- 如果這個 session 推不到新分支，先停下來告訴我，不要自己想辦法繞過。
- 依下面的順序一個一個做。PR 之間多半會在 `CHANGELOG.md` 的 `[Unreleased]` 衝突：前一個 merge 後，把 main 合併進還開著的分支（用 merge，不要 rebase 或 force-push），再解衝突。
- PR 標題和 commit 都用 Conventional Commits。commit 和 PR 描述結尾的 attribution 照 harness 給的寫；除此之外，repo 裡任何檔案、commit、PR 都不要寫模型名稱。

**開 PR 前的必做檢查**（全部乾淨才開 PR）
1. `go fmt ./...`、`go mod tidy`，兩者都不能產生 diff。安裝工具時不要在模組目錄裡執行，否則會改到 `go.sum`。
2. `go vet ./...`、改動套件的 `go test -race`、`make lint`、`make sast`、`make semconv-check`、`make adr-check`。
3. 改了程式碼（PR 10、以及 godoc 以外的任何 `.go` 改動）就要做 mutation 驗證：把修正暫時拿掉，確認測試或檢查會失敗，再放回去。純文件 PR 不需要。
4. 跑 `/code-review` 審自己的 diff，有問題就修好再審，沒問題才開 PR。
5. 文件裡提到的每個函式、選項、路徑、指令，都要對照目前的程式碼或檔案確認存在。用到任何 semconv attribute key，都要用 `.agents/skills/verify-semconv-attributes` 這個 skill 確認。
6. `CHANGELOG.md`：會影響使用者的改動（範例行為、文件裡更正的錯誤說明）在 `[Unreleased]` 加條目；純粹的錯字或內部整理可以不加，自己判斷，PR 描述裡說明理由。

**開 PR 後**
- 訂閱 PR 動態，處理 Codex、CodeRabbit 的意見和 CI 失敗，直到 CI 全綠、沒有衝突。
- CodeRabbit 有免費額度限制，被擋住時不用等它，Codex 和自己的 `/code-review` 沒問題就可以。
- 不要 merge、不要 approve，也不要建排程或定時檢查。
- 在 GitHub 上留言時，結尾要加 `\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_`。

**已知的環境狀況**
- 本地跑不了 govulncheck（proxy 擋住 vuln.go.dev），CI 有跑。
- 本地的 golangci-lint 可能是用舊版 Go 編譯的，跑 go1.26 的模組會報錯。這時以 CI 的 golangci-lint 結果為準，PR 描述裡註明。
- 本地沒有 kind 叢集，`kubectl` 相關的行為無法實際驗證。
- 在指令文字裡寫 `\uXXXX` 這類跳脫字元，可能被工具轉成實際字元。需要時用檔案工具寫入，再用 `cat -A` 確認。
- 透過 proxy 刪不了遠端分支，不用嘗試。

**溝通**
- 一律用繁體中文回覆我。
- 提到項目時不要只寫代號，要說明它是什麼問題。
- 用詞精確，不誇大。

### PR 11　`docs(guide): add an integration contract and a custom-metrics section`

報告第 4.2 節「各整合之間的合約不一致」，加上 2026-09-14 報告裡「自訂 metrics 沒有文件」那一項。

**A. 整合的共同合約（在 `docs/guide.md` 新增一段）**
- 寫下 #133 定下的 nil 規則：
  - 建構函式能回傳 error 的，傳入 nil tracer / meter provider 就回錯誤；
  - 不能回傳 error 的（gin `Middleware`、http `NewServerHandler` / `NewTransport`、resty `Wrap` / `NewClient`、mongo `NewMonitor`），換成 no-op；
  - 任何情況都不會用到 OTel 全域。
- propagator 的現況照 `CHANGELOG.md` `[Unreleased]` 的 Fixed 段落寫：
  - gin、http、resty 傳 nil 會換成空的 propagator；
  - nats 會回錯誤；
  - minio 接受 nil，因為用不到；
  - mongo 雖然用不到，卻會回錯誤。
  
  如實寫出這個差異即可，不要改行為。
- 其他三項不一致（同一份 options 呼叫兩次 `mongo.Instrument` 會產生重複 span、錯誤訊息有沒有套件前綴、預設 pool 名稱的三種命名方式）**還沒修**，屬於第三波。這段只寫已經成立的規則，不要寫成已經統一了。可以加一句「其餘部分尚未統一」，但不要列出細節。

**B. 自訂 metrics（在 `docs/guide.md` 新增一段，README 加一句指向它）**

用 SDK 的 meter provider 建立應用自己的 instrument 時，要提醒的三個陷阱。寫之前每一點都對照程式碼確認：
1. **私有 registry：** SDK 的 `/metrics` 用自己的 Prometheus registry（看 `internal/metrics/metrics.go`），所以用 `promauto` 或 `prometheus.MustRegister` 註冊到預設 registry 的既有 metric，**不會**出現在 SDK 的 `/metrics` 上。寫明正確做法是透過 `obs.MeterProvider()` 建立 instrument。也寫下為什麼沒有提供「把預設 registry 接進來」的選項：先在 `docs/adr/` 和 `CHANGELOG.md` 找有沒有記錄過這個決定，有就引用，沒有就只寫現況，不要自己編理由。
2. **名稱會被加上單位後綴：** Prometheus exporter 會把單位和 `_total` 加到名稱上，例如 `Int64Counter("orders.processed")` 在 `/metrics` 上會變成 `orders_processed_total`。寫一個小測試或 scratch 程式實際確認輸出的名稱，不要憑記憶。
3. **以秒為單位的 histogram 預設 bucket 不對：** 沒有指定邊界的 `Float64Histogram` 會用 OTel 的預設邊界，那是為毫秒設計的，秒為單位時幾乎所有值都落在第一個 bucket。寫明要用 `metric.WithExplicitBucketBoundaries`，或 SDK 的 `WithInstrumentHistogramBuckets` / `DefaultLatencyBuckets`。先確認這些名稱在目前的 API 裡存在。

`examples/metrics` 如果還沒有示範自訂 instrument，加一個最小的示範；已經有就引用它。
